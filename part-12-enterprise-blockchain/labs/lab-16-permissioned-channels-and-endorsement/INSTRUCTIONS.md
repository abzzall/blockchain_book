# Implementation 16 — Permissioned channels and endorsement policies

## Outcome

You will implement, in a language of your choice, the parts of a permissioned
network that a public chain has no equivalent for: identities issued by an
organisation rather than generated by their holder, channels that are separate
ledgers rather than filtered views of one, endorsement policies that say whose
agreement a transaction needs, and the execute--order--validate sequence that
decides what actually commits.

You will then run the three ways a correctly-formed transaction still fails: it
does not satisfy the policy, it was simulated against a state that has since
moved, or its endorsing peers disagreed about what it should write.

**The task does not require any particular programming language.** A complete
reference solution in JavaScript is supplied, but every value recorded here
follows from the rules below rather than from any language choice.

This runs entirely offline. There is no network, no node software, no browser,
and no test assets.

## Safety and environment

This is a teaching model of the execute-order-validate flow, **not** Hyperledger
Fabric. It reproduces endorsement, read and write sets, and the validation that
rejects a stale transaction, so that the shape of the design is visible. It has
no membership service, no cryptographic identity, no ordering service, and no
network. Nothing here should be run as, or mistaken for, a permissioned ledger.

- Network: none. Everything is in memory.
- Assets: none.
- The identities here are plain records. Nothing cryptographic is being
  demonstrated, and nothing here should be mistaken for a certificate authority.

## Specification

Everything in this section is normative.

### Identity

An organisation issues identities. An identity is `{org, commonName, role,
serial}`, and the issuing organisation records it. An identity is **recognised**
by a membership service when the named organisation is one the channel knows,
that organisation issued an identity with that common name and matching serial,
and that common name has not been revoked.

Nothing self-generated is ever recognised. This is the whole difference from a
public chain, where a key pair requires no issuer and no authority is consulted.

### Endorsement policies

A policy is an expression over organisation names: a bare name, `AND` of terms,
`OR` of terms, or `n`-of a list of terms. A set of endorsing organisations
satisfies the policy when the expression evaluates true over that set.

The channel used here requires the supplier, together with either the carrier or
the auditor:

```
(Supplier AND (Carrier OR Auditor))
```

### Channels

A channel has its own membership, its own endorsement policy, its own world
state, and its own ledger. An organisation outside a channel does not receive
that channel's data at all; it is not sent it in a form it cannot read.

A world-state entry is a value and a version. The version starts at zero for a
key that has never been written and increases by one on each committed write.

### Execute, order, validate

1. **Execute.** The client sends a proposal to endorsing peers. Each peer
   simulates the chaincode against its own world state, recording a **read set**
   (each key read, with the version at which it was read) and a **write set**
   (each key written, with the value). Simulation changes nothing.
2. **Order.** The ordering service places transactions in an order. It does not
   execute them and does not validate them.
3. **Validate and commit.** For each ordered transaction, in order, check:
   - every endorsing peer produced the same write set, else `ENDORSEMENT_MISMATCH`;
   - the endorsing organisations satisfy the policy, else `ENDORSEMENT_POLICY_FAILURE`;
   - every key in the read set is still at the version that was read, else `MVCC_READ_CONFLICT`.

   If all three pass the status is `valid` and the write set is applied, each
   written key's version increasing by one. **Every transaction is appended to
   the ledger regardless**, carrying its status. An invalid transaction's writes
   are not applied.

### The scenario under test

Three organisations — `Supplier`, `Carrier`, `Auditor` — with identities `sam`,
`cara`, and `ada` respectively, plus `mallory`, a well-formed identity claiming
to be a Supplier client that the Supplier never issued.

Two channels: `shipments`, whose members are all three organisations and whose
policy is the one above; and `audit`, whose members are the Supplier and Auditor
only and whose policy is `Auditor`.

The chaincode under test is deterministic: read `shipments`, write it back
incremented by one, treating an unset key as zero.

## Command-line work

### Part A — Who is recognised

```bash
npm run identity
```

Record whether mallory's identity is recognised. Note what happens to sam after
revocation, and what that implies about checking an identity offline.

### Part B — Policies

```bash
npm run endorse
```

Record whether `{Supplier, Auditor}` and `{Carrier, Auditor}` satisfy the policy,
and the status of a transaction endorsed by the supplier alone and by the
supplier with the carrier. Note that all three transactions reached the ledger.

### Part C — Channels

```bash
npm run channels
```

Record whether the audit channel holds any value for `shipments` after the
shipments channel has been written to.

### Part D — Concurrency

```bash
npm run conflict
```

Two clients propose against the same state before either commits. Record both
statuses, the resulting value, and the number of ledger entries.

### Part E — Non-determinism


## Troubleshooting and reset

- Nothing here writes to disk, so there is nothing to reset.
- If both concurrent transactions commit, your read set is probably not
  recording the version, or validation is not comparing it.
- If the non-deterministic transaction commits, check that you compare the write
  sets of **all** endorsing peers rather than trusting the first.
- If an invalid transaction is missing from the ledger, remember that the ledger
  records every ordered transaction and marks it, rather than discarding it.
