# Implementation 12 — Capstone: a certificate registry

## Outcome

You will implement a working contract from a specification, not from a
skeleton with the answers filled in. A registry issues course certificates,
records who issued them and to whom, lets certificates be revoked without being
erased, and lets anybody check a certificate's validity. An acceptance suite of
eighteen tests defines what "working" means; your job is to make it pass, and
then to go past it.

This is the capstone. It assumes everything from Chapters 14 to 25 and the
security material in Chapter 42.

## Safety and environment

- Network: Hardhat's in-process local chain. Nothing leaves your machine.
- Assets: none. This contract holds no value and has no payable function.
- If you extend the capstone with a frontend or a testnet deployment, use test
  assets only and a dedicated key held outside the repository.

## The specification

### Roles

The account that deploys the registry is its **admin**, and is an issuer from
the moment of deployment. Only the admin may add or remove issuers. Adding an
account that is already an issuer, or removing one that is not, is an error, as
is naming the zero address. Both changes emit an event naming the account
affected and the account that made the change.

### Identity

A certificate's id is `keccak256(abi.encode(recipient, issuer, courseName))`.
It must be a `pure` function of exactly those three arguments, so that anybody
holding a certificate can recompute its id without asking the registry
anything. Two certificates agreeing on all three are the same certificate.

### Issuing

Any issuer may issue a certificate to a recipient for a named course with a
grade. The registry stores the recipient, the issuer, the course name, the
grade, the time of issue, whether it has been revoked, and the reason if it
has. It refuses the zero address, an empty course name, and any attempt to
issue a certificate that already exists. It keeps, for each recipient, the ids
of their certificates in the order they were issued.

### Revocation

Any issuer may revoke any certificate, giving a non-empty reason. Revoking
does not delete the certificate and does not reduce `totalIssued`: the record
stays readable, now marked revoked and carrying its reason. Revoking twice is
an error, as is revoking a certificate that does not exist.

### Reading

`get` returns the whole record, and reverts if the certificate does not exist.
`isValid` returns true only for a certificate that exists and has not been
revoked, and returns false — rather than reverting — for one that does not
exist. `certificatesOf` returns a recipient's ids, and an empty array for
somebody with none.

## Command-line work

```bash
cd part-16-capstone-projects/labs/lab-12-capstone-certificate-registry
npm run build
npm run accept
```

Before you write anything, all eighteen tests fail. That is the starting point.

The capstone deliberately ships unimplemented, so it has no `test` script and
is skipped by the repository-wide test run. `npm run accept` is its suite.

Work through them. `npm run accept` runs the acceptance suite, and
`npx hardhat test nodejs --grep "issuing"` runs one group at a time, which is
the sane way to make progress.

## Going past the suite

The acceptance suite is deliberately incomplete, and passing it is not evidence
that your contract is good. Write your own tests, and record them in
`RESULTS.md`. Things it does not check, and you should think about:

- what happens to a certificate when the issuer who issued it is later removed;
- whether an issuer removed from the roll can still revoke;
- what a very long course name costs, and whether that is a problem;
- whether anything in your implementation grows without bound as certificates
  accumulate, and what that costs a caller;
- whether every error in your contract can actually be triggered.

## What to record

The six values in `RESULTS.md`, the tests you added, and the answers to seven
questions.

The `certificateId` value is worth noticing: it is fixed by the specification,
not by your implementation, so the marker knows what it must be before seeing
your code. If yours differs, you have encoded the arguments differently, and
anyone trying to recompute one of your ids independently would fail.

## What to explain

`RESULTS.md` asks seven questions: what a deterministic id buys and what it
prevents; why revocation preserves the record; what happens if the admin key is
lost and if it is stolen; why `isValid` and `get` behave differently on a
missing certificate; a design decision you made and defended; two Chapter 42
security topics applied to your own code, honestly, including where nothing
addresses them; and finally what a third party can and cannot conclude from a
valid certificate.

That last one is the capstone's real question. The registry establishes that an
issuer said something. Whether the course happened, whether the recipient
attended it, and whether the issuer was entitled to award it are all outside
what any chain can settle, and your answer should say so plainly.

## Troubleshooting

- A `NotImplemented` revert means you have not yet replaced that body.
- If `certificateId` disagrees with the expected value, check that you used
  `abi.encode` and not `abi.encodePacked`; the two differ, and only one of them
  is unambiguous when a string is involved.
- If an event assertion fails on an argument you believe correct, check the
  order and the `indexed` markers against the supplied event declaration.
- A test that fails only when run with others usually means state is leaking
  between tests; each acceptance test deploys its own registry.
